# Архитектура

[English](../architecture.md) | Русский

Centaur — gateway-прокси перед [Ollama](https://ollama.com). Коннекторы стоят
рядом с локальными Ollama и поднимают к gateway исходящие TCP-соединения —
туннели; клиенты обращаются к gateway как к обычному Ollama API.

```
                      туннель (TCP)
client ──▶ gateway ─────────────────▶ connector ──▶ Ollama (локально)
             proxy.address          pool.address     target.address

prometheus ──▶ gateway (metrics.address, GET /metrics)
```

Смысл схемы в том, что до Ollama снаружи достучаться нельзя: gateway не открывает
портов на стороне Ollama — соединение всегда инициирует коннектор, поэтому
достаточно исходящего доступа к gateway.

## Одноразовые туннели

Туннель обслуживает ровно один клиентский запрос. После ответа соединение
закрывается, и коннектор поднимает новое. Так переподключение не зависит от
состояния клиентского соединения: если связь порвалась, следующий запрос поедет по
новому туннелю, а не по «подвисшему» старому.

Коннектор держит не один туннель, а пул из `pool.tunnels` штук параллельно: в
простое они готовы принять запрос, под нагрузкой обслуживают до `pool.tunnels`
запросов одновременно. Поэтому `pool.tunnels` — это и степень параллелизма, и
потолок: запросы сверх числа свободных туннелей получают `503`.

## Регистрация и handshake

1. Коннектор отправляет `POST /api/v1/tunnels/register` на HTTP API пула
   (заголовок `ApiKey`, тело `{"models": [...]}`) и получает `token`.
2. Коннектор подключается к TCP-адресу пула и первым делом пишет 16-байтовый
   `token` — это handshake.
3. Gateway по токену привязывает соединение к зарегистрированному туннелю: до
   handshake туннель в состоянии `pending`, после — `ready`.
4. Клиентский запрос приходит на `proxy.address`. Gateway разбирает имя модели из
   тела запроса, находит свободный туннель, поддерживающий эту модель, и
   проксирует запрос по туннелю.
5. Коннектор принимает запрос из туннеля и проксирует его в локальную Ollama.
6. После ответа туннель закрывается, коннектор поднимает новый. `Serve` запускает
   `pool.tunnels` таких воркеров, поэтому пул не пустеет.

## Пул и вычистка мёртвых туннелей

Пул не раздаёт мёртвые туннели:

- **перед выдачей** gateway заглядывает во входящий поток соединения и не
  потребляет данные (`MSG_PEEK` на Unix-сокетах): если коннектор закрыл или оборвал
  соединение, туннель выбрасывается;
- **фоновый обход реестра** раз в `sweepInterval` (5 секунд) убирает туннели, до
  которых не дошёл трафик, — включая `pending`, у которых handshake так и не
  завершился.

Без этого после падения коннектора его туннели оставались бы в пуле «готовыми»,
выдавались бы клиентам, и те получали бы `502` на запись в закрытое соединение.
Сколько туннелей выброшено, видно по `centaur_gateway_tunnel_stale_total`.

Остаётся случай, который так не поймать: обрыв без FIN/RST («чёрная дыра» — связь
пропала молча). Его видно только по TCP-keepalive туннельного сервера (период
30 секунд, обнаружение — около 5 минут), поэтому запрос, попавший в такой туннель,
может закончиться `502`.

## Почему метрики на отдельном адресе

Метрики отдаются на `metrics.address` (`GET /metrics`), а не на `proxy.address`:

- свой порт удобно слушать на loopback и не публиковать на сетевом периметре;
- Prometheus скрейпит gateway независимо от клиентского трафика;
- `proxy.address` остаётся точной копией Ollama API — без лишних ручек.

## Карта пакетов

| Путь | Назначение |
| --- | --- |
| `cmd/gateway` | бинарь gateway: конфиг, запуск/остановка серверов |
| `cmd/connector` | бинарь коннектора: конфиг, запуск/остановка клиента |
| `internal/api/proxy_server.go` | `ProxyServer` — клиентский HTTP-сервер |
| `internal/api/metrics_server.go` | `MetricsServer` — HTTP-сервер метрик |
| `internal/tunnel/service.go` | сторона gateway: обратный прокси, разбор модели, маршрутизация |
| `internal/tunnel/registry.go` | реестр туннелей: `Register`/`Bind`/`Acquire` |
| `internal/tunnel/tunnel.go` | структура `Tunnel` и состояния `pending`/`ready` |
| `internal/tunnel/tunnel_server.go` | TCP-сервер пула: handshake и выдача туннелей |
| `internal/tunnel/api_server.go` | HTTP API пула (регистрация) и `AuthMiddleware` |
| `internal/tunnel/client.go` | клиент коннектора: регистрация, туннель, прокси в Ollama |
| `internal/tunnel/model.go` | список инференс-ручек и разбор имени модели из тела |
| `internal/tunnel/auth.go` | проверка API-ключа |
| `internal/tunnel/dto.go` | DTO регистрации туннеля |
| `internal/metrics` | реестр Prometheus, метрики gateway, обработчик `/metrics` |

## Дизайн-заметки

- Инфо/админ-ручки Ollama gateway не проксирует: он выполняет инференс, а не
  управляет удалённой Ollama.
- Тело запроса больше 1 МиБ (константа `maxModelBodyBytes`) не разбирается ради
  имени модели — так устроен `/api/chat` с крупными `images`. Тело уходит дальше
  целиком, потоком, но маршрутизация по модели для такого запроса недоступна.
- WebSocket/Upgrade (`101 Switching Protocols`) туннель не поддерживает: Ollama его
  не использует.
- `pool.*` на двух сторонах означает разное: gateway **слушает** на
  `pool.address`/`pool.apiAddress`, коннектор **ходит** по ним. Оба бинарника
  валидируют формат адресов при старте и падают с внятной ошибкой.
